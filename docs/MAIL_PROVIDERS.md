# Почтовые провайдеры WB Insight

## Назначение

Почтовая подсистема WB Insight не зависит от конкретного поставщика доставки. Высокоуровневые сценарии — подтверждение email, восстановление доступа, системные уведомления, тестовая отправка и кампании — работают через общий контракт адаптера.

Текущие адаптеры:

- `smtp` — классический SMTP-транспорт;
- `rusender` — HTTPS API RuSender через исходящий порт `443`;
- `resend` — HTTPS API Resend через исходящий порт `443`.

RuSender и Resend являются взаимозаменяемыми HTTPS-адаптерами на уровне бизнес-логики. Регистрация, recovery, очередь и кампании не должны импортировать классы конкретного провайдера.

## Сравнение текущих адаптеров

| Возможность | SMTP | RuSender | Resend |
| --- | --- | --- | --- |
| Транзакционные письма | да | да | да |
| Исходящий порт без SMTP | нет | `443` | `443` |
| Маркетинговые кампании | да | нет в текущем transactional endpoint | да |
| RFC-заголовки кампаний | да | нет | да |
| One-click unsubscribe | да | нет | да |
| Reply-To | да | нет в текущем адаптере | да |
| Idempotency key | нет на уровне SMTP | да | да |
| Отдельный ID ключа | нет | да | нет |

Для маркетинговых кампаний одного capability адаптера недостаточно: в WB Insight также должны быть включены кампании и настроены `MAIL_UNSUBSCRIBE_BASE_URL` и `MAIL_UNSUBSCRIBE_HMAC_KEY`.

## Runtime-контракт

Общий runtime хранит нейтральные API-поля:

- `API_BASE_URL` — доверенный endpoint адаптера;
- `API_KEY_ID` — идентификатор ключа, если он требуется провайдеру;
- `API_TOKEN` — секрет API;
- `API_TIMEOUT_SECONDS` — timeout HTTPS-запроса.

Поля SMTP остаются отдельными, потому что они описывают другой тип транспорта: host, port, STARTTLS, username/password и Reply-To.

Исторические имена `RUSENDER_*` принимаются runtime только как переходная совместимость. Внутреннее состояние сохраняется в нейтральных `API_*` полях. Новые адаптеры не должны использовать `RUSENDER_*`.

## Возможности адаптера

Каждый адаптер объявляет capabilities и метаданные конфигурации. Бизнес-логика не проверяет название провайдера.

Основные capabilities:

- транзакционная отправка;
- маркетинговые кампании;
- произвольные и RFC-заголовки;
- one-click unsubscribe;
- Reply-To;
- preview/preheader;
- idempotency key;
- TLS/PTR на стороне провайдера;
- тип транспорта и исходящий порт.

Для HTTPS API адаптер дополнительно объявляет:

- доверенный API endpoint;
- порт;
- требуется ли отдельный ID ключа;
- должен ли ID ключа быть числовым;
- имена ENV-переменных для endpoint, ID ключа, токена и timeout.

Control Panel получает эти метаданные через каталог провайдеров. Поэтому интерфейс может показывать только те поля и функции, которые действительно поддерживает выбранный адаптер.

## Настройка через Control Panel

Экран `Панель управления → Рассылки → Почтовый шлюз` строит форму по capability-контракту выбранного адаптера, а не по проверке его имени.

Правила интерфейса:

- переключатель пользовательских кампаний виден только при `marketing=true`;
- `Reply-To` виден только при `reply_to=true`;
- поле `ID ключа` показывается только если адаптер объявляет `requires_key_id=true`;
- HTTPS endpoint берётся из доверенной конфигурации адаптера и не редактируется в браузере;
- API-токен после сохранения не возвращается клиенту, отображается только его короткий fingerprint;
- при смене провайдера старые credentials не переиспользуются автоматически;
- тестовая отправка всегда идёт через фактически выбранный и сохранённый транспорт.

Это означает, что Resend может быть настроен в Control Panel как HTTPS-транспорт для системных писем и кампаний без появления RuSender-специфичных полей. RuSender, напротив, показывает `ID ключа` и не предлагает включить кампании, потому что таковы capabilities текущего адаптера.

Regression-тесты запрещают возвращать в frontend прямые условия вида `provider === 'rusender'` или `provider === 'resend'` и проверяют, что `enabled`, `Reply-To` и `key_id` формируются по capabilities.

## Resend

Адаптер `resend` использует `POST /emails` через `https://api.resend.com` и bearer API key.

В WB Insight используются:

- `from`, `to`, `subject`, `text`, `html`;
- `reply_to`, если он настроен;
- пользовательские заголовки, включая служебные заголовки кампаний;
- `Idempotency-Key` для защиты от повторной отправки;
- идентификатор ответа Resend как `provider_message_id`.

`preview_title` встраивается в HTML как скрытый preheader, потому что API Resend не требует отдельного поля preview.

Для production отправляющий домен необходимо предварительно подтвердить у Resend. SPF/DKIM и фактическую доставляемость нужно проверять по настройкам домена и исходнику реально доставленного письма.

ENV-конфигурация:

```text
MAIL_PROVIDER=resend
RESEND_API_BASE_URL=https://api.resend.com
RESEND_API_TOKEN=<секрет>
RESEND_TIMEOUT_SECONDS=10
SMTP_FROM_EMAIL=no-reply@ваш-домен.ru
SMTP_FROM_NAME=WB Insight
SMTP_REPLY_TO_EMAIL=support@ваш-домен.ru
```

Для кампаний дополнительно:

```text
MAIL_DELIVERY_ENABLED=true
MAIL_UNSUBSCRIBE_BASE_URL=https://ваш-домен.ru/api/account/mail/unsubscribe
MAIL_UNSUBSCRIBE_HMAC_KEY=<стойкий независимый секрет>
```

## Безопасность

Для HTTPS API endpoint задаётся адаптером и не принимается как произвольный URL из браузера. Это исключает перенаправление сохранённого bearer-токена на сторонний узел через административную форму.

API-токены и SMTP-пароли хранятся в зашифрованном виде. В Control Panel секрет обратно не возвращается; для API-токена допускается только короткий SHA-256 fingerprint.

Сырые тела ошибок внешних провайдеров не возвращаются пользователю и не должны попадать в безопасный код ошибки. Сохраняется только ограниченный машинный код, если он соответствует допустимому формату.

В production HTTPS API должен использовать `https://`. SMTP должен использовать STARTTLS.

## Заблокированные SMTP-порты

Если хостер блокирует исходящие SMTP-порты, используется HTTPS-адаптер:

```text
WB Insight -> HTTPS :443 -> Mail API -> почтовые серверы получателей
```

Поэтому блокировка `25`, `465` или `587` не мешает отправке через RuSender или Resend.

Для сценария, где нужны и системные письма, и маркетинговые кампании без SMTP, текущим подходящим адаптером является `resend`: он работает через `443` и поддерживает необходимые заголовки кампаний.

## Добавление нового HTTPS-провайдера

Новый провайдер реализуется отдельным адаптером в `backend/integrations/mail/` и регистрируется в таблице фабрик транспорта. Адаптер должен:

1. объявить `code`, отображаемое имя и capabilities;
2. задать доверенный API endpoint и порт;
3. указать, нужен ли ID ключа;
4. объявить ENV-атрибуты для собственной конфигурации;
5. реализовать `send(...)` и возвращать `MailDeliveryReceipt`;
6. преобразовывать ошибки внешнего API в общий `MailProviderError` с безопасным кодом и русским пользовательским сообщением;
7. иметь regression-тесты на успешную отправку, временные и постоянные ошибки, отсутствие утечки секрета.

Очередь `MailMessage`, `mail_service`, регистрация, recovery и обработчики Control Panel при этом изменяться не должны.

## Ограничения текущих адаптеров

Текущий transactional endpoint RuSender не заявляет поддержку используемых WB Insight RFC 8058 заголовков маркетинговой рассылки. Поэтому его capability `marketing=false`.

SMTP и Resend поддерживают кампании при включённой доставке и настроенном one-click unsubscribe.
