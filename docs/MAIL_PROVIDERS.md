# Почтовые провайдеры WB Insight

## Назначение

Почтовая подсистема WB Insight не должна зависеть от конкретного поставщика доставки. Высокоуровневые сценарии — подтверждение email, восстановление доступа, системные уведомления, тестовая отправка и кампании — работают через общий контракт адаптера.

Текущие адаптеры:

- `smtp` — классический SMTP-транспорт;
- `rusender` — HTTPS API RuSender через исходящий порт `443`.

RuSender является текущей реализацией HTTPS-доставки, но не является обязательной частью бизнес-логики.

## Runtime-контракт

Общий runtime хранит нейтральные API-поля:

- `API_BASE_URL` — доверенный endpoint адаптера;
- `API_KEY_ID` — идентификатор ключа, если он требуется провайдеру;
- `API_TOKEN` — секрет API;
- `API_TIMEOUT_SECONDS` — timeout HTTPS-запроса.

Поля SMTP остаются отдельными, потому что они описывают другой тип транспорта: host, port, STARTTLS, username/password и Reply-To.

Исторические имена `RUSENDER_*` принимаются runtime только как переходная совместимость. Внутреннее состояние сохраняется в нейтральных `API_*` полях. Новые адаптеры не должны использовать `RUSENDER_*`.

## Возможности адаптера

Каждый адаптер объявляет capabilities, а также метаданные конфигурации. Бизнес-логика не проверяет название провайдера.

Основные capabilities:

- транзакционная отправка;
- маркетинговые кампании;
- произвольные и RFC-заголовки;
- one-click unsubscribe;
- Reply-To;
- preview/preheader;
- idempotency key;
- TLS/PTR на стороне провайдера;
- тип транспорта и исходящий порт.

Для HTTPS API адаптер дополнительно объявляет:

- доверенный API endpoint;
- порт;
- требуется ли отдельный ID ключа;
- должен ли ID ключа быть числовым;
- имена ENV-переменных для endpoint, ID ключа, токена и timeout.

Это позволяет подключить следующий HTTPS-провайдер без добавления его имени в `mail_service`, обработчики Control Panel и клиентские lifecycle-сценарии.

## Безопасность

Для HTTPS API endpoint задаётся адаптером и не принимается как произвольный URL из браузера. Это исключает перенаправление сохранённого bearer-токена на сторонний узел через административную форму.

API-токены и SMTP-пароли хранятся в зашифрованном виде. В Control Panel секрет обратно не возвращается; для API-токена допускается только короткий SHA-256 fingerprint.

В production HTTPS API должен использовать `https://`. SMTP должен использовать STARTTLS.

## Заблокированные SMTP-порты

Если хостер блокирует исходящие SMTP-порты, используется HTTPS-адаптер. Такой транспорт работает через обычный исходящий порт `443`:

```text
WB Insight -> HTTPS :443 -> Mail API -> почтовые серверы получателей
```

Поэтому блокировка `25`, `465` или `587` не мешает транзакционной почте через HTTPS API.

## Добавление нового HTTPS-провайдера

Новый провайдер реализуется отдельным адаптером в `backend/integrations/mail/` и регистрируется в таблице фабрик транспорта. Адаптер должен:

1. объявить `code`, отображаемое имя и capabilities;
2. задать доверенный API endpoint и порт;
3. указать, нужен ли ID ключа;
4. объявить ENV-атрибуты для собственной конфигурации;
5. реализовать `send(...)` и возвращать `MailDeliveryReceipt`;
6. преобразовывать ошибки внешнего API в общий `MailProviderError` с безопасным кодом и русским пользовательским сообщением;
7. иметь regression-тесты на успешную отправку, временные и постоянные ошибки, отсутствие утечки секрета.

Очередь `MailMessage`, `mail_service`, регистрация, recovery и обработчики Control Panel при этом изменяться не должны.

## Ограничения текущих адаптеров

Текущий transactional endpoint RuSender не заявляет поддержку используемых WB Insight RFC 8058 заголовков маркетинговой рассылки. Поэтому его capability `marketing=false`.

SMTP поддерживает кампании при включённой доставке и настроенном one-click unsubscribe.

Добавление HTTPS-провайдера с полноценной поддержкой marketing возможно отдельным адаптером без изменения высокоуровневой почтовой архитектуры.
