# WB Insight — безопасность

## Совместимость шифрования токенов Wildberries

Новые WB-токены шифруются производным Fernet-ключом, зависящим от `API_TOKEN_ENCRYPTION_KEY` и идентификатора пользователя. Это изолирует зашифрованные данные разных пользователей при одном мастер-ключе.

До 30 апреля 2026 года использовался прямой Fernet-ключ `API_TOKEN_ENCRYPTION_KEY`. Во время работы сохраняется только обратная совместимость чтения: сначала пробуется текущая пользовательская схема, затем историческая. После успешной ручной проверки устаревшая запись автоматически перешифровывается текущей схемой.

Резервное чтение старого формата не означает поддержку старого мастер-ключа после его ротации. Если зашифрованное значение нельзя прочитать ни текущим пользовательским ключом, ни историческим форматом текущего мастер-ключа, секрет не восстанавливается: API возвращает безопасную ошибку и требует удалить подключение и добавить новый WB-токен.

## Основные принципы

WB Insight обрабатывает чувствительные данные продавца, поэтому правила безопасности являются частью контракта продукта, а не только настройкой развёртывания.

## Сессия пользователя

- короткоживущий токен доступа хранится только в памяти клиентского приложения;
- сессия обновления использует HttpOnly cookie;
- в боевом окружении cookie работает только по HTTPS;
- токены доступа и обновления содержат `session_version`, которую сервер проверяет на защищённых запросах и при обновлении сессии;
- `POST /auth/logout` очищает cookie и атомарно увеличивает серверную `session_version`; поэтому ранее выданные токены пользователя становятся недействительными на всех устройствах;
- повторный logout со старым или уже отозванным токеном идемпотентен и всё равно очищает cookie;
- CI проверяет, что токен доступа не возвращается в постоянное хранилище браузера.

## Защита публичной авторизации

Публичные вход, регистрация и предварительные проверки идентификаторов проходят общий защитный слой до бизнес-обработчика.

- `/auth/login` ограничивается одновременно по клиентскому IP и непрозрачному идентификатору email;
- `/auth/registration` ограничивается по IP и email;
- `/auth/check-email`, `/auth/check-phone`, `/auth/check-inn` больше не раскрывают, существует ли аккаунт: после проверки формата они возвращают одинаковый успешный результат;
- email, телефон, ИНН и IP не сохраняются в Redis-ключах открытым текстом: для ключа используется HMAC-SHA256 с серверным секретом;
- `X-Real-IP` учитывается только когда непосредственное соединение пришло от локального обратного прокси;
- превышение лимита возвращает HTTP `429`, код `AUTH_RATE_LIMITED` и заголовок `Retry-After`;
- в боевом окружении Redis является обязательной частью защиты: если счётчик недоступен, публичная авторизация закрывается с HTTP `503` и `AUTH_RATE_LIMIT_UNAVAILABLE`, а не продолжает работу без ограничения частоты;
- вне боевого окружения при недоступном Redis разрешён локальный счётчик процесса, чтобы разработка не зависела от внешнего Redis.

Пределы настраиваются переменными `AUTH_LOGIN_RATE_*`, `AUTH_CHECK_RATE_*`, `AUTH_REGISTRATION_RATE_*`; канонические значения приведены в `.env.production.example`.

## Права доступа

Backend является источником истины для ролей, владения данными и области кабинета. Проверки маршрутов клиентского приложения используются только для интерфейса и не заменяют серверную авторизацию.

## Подключения маркетплейса

Данные доступа к кабинету проверяются до сохранения, хранятся в защищённом виде и после сохранения не возвращаются в браузер. Детальный контракт WB находится в `WB_ACCESS_TOKEN_REQUIREMENTS.md`.

## Секреты окружения

Секреты боевого окружения задаются через переменные развёртывания или хранилище секретов. Они не должны попадать в git, клиентскую сборку, снимки экрана, журналы приложения или доказательства релиза. Имена обязательных параметров приведены в `CONFIGURATION.md` и `.env.production.example`.

## Оплата

Клиентское перенаправление не подтверждает оплату. Подписка активируется только после серверной проверки статуса у платёжного провайдера. Идемпотентность защищает от повторной активации одной оплаты.

## Юридические подтверждения

Backend проверяет точную версию принятого документа и сохраняет неизменяемое подтверждение. Технические признаки сохраняются в минимизированном с точки зрения приватности виде.

## CORS и шлюз

Боевое окружение использует nginx-шлюз в рамках одного origin. CORS настраивается точным списком разрешённых HTTPS-origin.

## Безопасность зависимостей

CI клиентской части выполняет проверку зависимостей с порогом high. Backend CI выполняет `pip-audit` для production-зависимостей. Найденные уязвимости должны быть исправлены или формально оценены до повышения стадии релиза.

## База данных и резервные копии

Схема управляется только Alembic. Скрипты резервного копирования создают зашифрованный файл и контрольную сумму; готовая к боевому использованию резервная копия должна храниться вне основного сервера и проходить проверку восстановления.

## Логирование

Журналы не должны содержать значения сессий, данные доступа маркетплейса, банковские данные или содержимое запросов с чувствительными полями. Для диагностики используются безопасные идентификаторы и агрегированные операционные сигналы.

## Проверка перед RC

До `1.0.0-rc.1` должны быть подтверждены аудит зависимостей, HTTPS/cookie/CORS, изоляция арендаторов, хранение production-секретов, проверка WB/Сбер, восстановление резервной копии и проверка жизненного цикла аккаунта.
