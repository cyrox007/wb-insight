# WB Insight — данные и метрики

Цель документа — зафиксировать смысл показателей и правила проверки, не дублируя SQL/Python формулы построчно. Каноническая реализация формул находится в backend semantic/business layer и покрывается тестами.

## Источники данных

### Wildberries

WB Insight получает через официальные API отдельные домены данных:

- заказы;
- продажи/возвраты;
- товары/content;
- остатки;
- цены;
- реклама;
- воронка;
- платное хранение;
- финансовые отчёты/операции.

Один и тот же бизнес-процесс может иметь разные даты и значения в operational и finance API. Поэтому система не должна подменять финансовую реализацию суммой operational orders.

### Данные продавца

WB не знает часть управленческих параметров, поэтому пользователь добавляет:

- историческую себестоимость;
- собственные расходы;
- налоговую ставку/профильные параметры;
- месячный план выручки.

## Account scope

Все факты относятся к конкретному marketplace account. При агрегировании нескольких кабинетов backend должен сначала применить разрешённый account scope и только потом строить метрики.

## Период и сравнение

Dashboard принимает `start_date`/`end_date`. Изменение KPI сравнивается с сопоставимым предыдущим периодом. Временные границы должны учитывать semantic правила конкретного источника и timezone.

## Канонический финансовый слой

Начиная с P115 финансовые KPI «Обзора» и «Юнит-экономики» считаются через один semantic layer. Один и тот же кабинет и период не должны иметь разные определения прибыли, ДРР, выручки, выплат, логистики или хранения в разных экранах.

### Политика знаков

Продажа увеличивает выручку, количество, выплату и списание себестоимости. Возврат уменьшает эти показатели. Для строк Wildberries знак операции определяется бизнес-типом операции, а не случайным знаком исходного денежного поля.

К продажам относятся обычная `Продажа` и соответствующая `Коррекция продаж`. К возвратам относятся `Возврат`, возвратная `Коррекция продаж` и `Коррекция возвратов`.

### Выручка и база прибыли

Для пользовательского KPI «Выручка» используется чистая сумма продаж с СПП после возвратов.

Для расчёта управленческой прибыли используется чистая сумма продаж без СПП после возвратов, после чего вычитается полный набор учтённых расходов и добавляются применимые финансовые корректировки.

### Расходы Wildberries

Общий P&L учитывает финансовые расходы из всех строк Finance API, а не только из строк `Продажа`/`Возврат`. В расходную базу входят, когда они присутствуют в отчёте:

- комиссия WB;
- доставка и обратная логистика;
- перевыставленная логистика;
- эквайринг;
- хранение;
- платная приёмка;
- штрафы;
- удержания;
- применимые налоговые компоненты вознаграждения WB.

Строка без `nmId` не отбрасывается. Внутри financial facts она хранится как нераспределённая операция кабинета и влияет на общий P&L, но не приписывается произвольному товару. API отдельно показывает сумму нераспределённых расходов, чтобы разница между итогом кабинета и суммой товарных строк была объяснима.

### Реклама, налог и собственные расходы

Рекламные расходы берутся из фактического advertising layer. Налог считается от чистых продаж с СПП по ставке пользователя. Ручные расходы входят в общий P&L; расход с SKU участвует и в товарной строке, расход без SKU остаётся только на уровне кабинета.

### Прибыль

Каноническая формула уровня кабинета:

`прибыль = продажи без СПП после возвратов + финансовые корректировки - себестоимость - расходы WB - налог - реклама - собственные расходы`.

Формула должна использоваться одинаково в Overview, Unit Economy и в контрольной сверке финансового слоя.

### ДРР

Канонический ДРР текущей версии:

`ДРР = рекламные расходы / чистые продажи с СПП × 100%`.

Старая spreadsheet-модель могла использовать заказы как знаменатель. Это другая бизнес-метрика и не должна называться тем же ДРР без явного переименования.

### Маржинальность и рентабельность

Маржинальность:

`маржинальность = прибыль / чистые продажи без СПП × 100%`.

Рентабельность текущего P&L:

`рентабельность = прибыль / все учтённые расходы × 100%`.

Ratio-метрики при агрегировании по товарам/кабинетам считаются из агрегированных числителей и знаменателей, а не средним арифметическим процентов отдельных строк.

## Основные KPI Overview

### Заказано
Сумма operational orders за выбранный период. Сопровождается количеством заказанных единиц.

### Выручка
Чистые продажи с СПП после возвратов за выбранный период. Не равна автоматически «заказано» и не равна «к выплате».

### Прибыль
Управленческий результат по канонической формуле выше. Overview не имеет отдельной упрощённой формулы прибыли.

### К выплате
Показатель из финансового слоя WB с бизнес-знаком возвратов и корректировок. Его нельзя вычислять простой разницей выручки и одной комиссии.

### Выкуп
Отношение продаж/выкупов к заказам в рамках semantic definition текущей версии.

### Средняя цена заказа
Средняя сумма на заказанную единицу согласно текущей реализации.

## Себестоимость во времени и достоверность прибыли

COGS имеет `effective_from`. Для каждой финансовой операции применяется версия себестоимости, действовавшая на дату этой операции. Новая цена закупки не должна задним числом помечать раннюю продажу как обеспеченную себестоимостью.

Если хотя бы для одной релевантной операции продажи/возврата себестоимость на её дату отсутствует, система:

- считает доступную оценку с нулём только для неизвестной части;
- возвращает `profit_complete=false`;
- возвращает процент покрытия и количество операций без себестоимости;
- явно предупреждает пользователя, что прибыль неполная.

Неполный расчёт нельзя визуально выдавать за финансово достоверный итог.

## Ручные расходы

Расход имеет дату, account scope и optional SKU. Без SKU он относится к общему P&L; с SKU может участвовать в товарной экономике.

## План и прогноз

Месячный план — persistent target. Overview показывает:

- факт текущего месяца;
- план;
- процент выполнения;
- текущий прогноз;
- требуемую выручку в день;
- требуемое число заказов в день.

Факт текущего месяца использует ту же каноническую чистую выручку с СПП, что и Overview. Расчёт учитывает фактическую длину календарного месяца, а не фиксированные 30 дней.

## Inventory metrics

Inventory baseline использует фактические остатки и исторический спрос для оценки:

- stock cover;
- критического остатка;
- риска stockout;
- recommendation quantity.

Рекомендация не является гарантированным прогнозом спроса и требует проверки бизнес-ограничений поставки.

## Finance reconciliation

Reconciliation сравнивает финансовые факты с официальными summary/detail источниками WB и использует денежный tolerance. Для текущего baseline tolerance — 2 копейки там, где это предусмотрено reconciliation logic.

Reconciliation и управленческий P&L решают разные задачи: первый доказывает полноту/согласованность исходных денег WB, второй применяет каноническую бизнес-формулу с себестоимостью, рекламой, налогом и собственными расходами.

## ABC

Overview содержит ABC-анализ за выбранный период. Точный показатель ранжирования должен оставаться согласованным с backend реализацией текущей версии; при изменении методики требуется обновить этот документ и тесты.

## Data quality states

UI/API должны различать как минимум:

- данные готовы;
- идёт sync;
- capability недоступна из-за permissions;
- внешний API временно недоступен;
- credential недействителен;
- нет данных за выбранный период;
- прибыль неполная из-за отсутствующей исторической себестоимости.

Нельзя заменять отсутствие данных выдуманными demo KPI.

## Приёмочная сверка перед релизом

На реальном seller account выбираются фиксированные кабинет и периоды и сверяются доступные денежные/операционные показатели с официальными WB-источниками и исходной spreadsheet-моделью.

Минимальный набор:

- orders/sales/returns;
- revenue;
- WB commissions;
- logistics/storage;
- advertising;
- COGS;
- seller expenses;
- taxes;
- profit;
- payouts/reconciliation;
- inventory/prices;
- unit-economy ratios.

Для одинакового account scope и периода финансовые агрегаты Overview и Unit Economy обязаны совпадать с каноническим semantic layer. Отдельно проверяются:

- возврат с положительными исходными суммами WB уменьшает чистую выручку и выплату;
- отдельные строки `Логистика`, `Хранение`, `Удержание`, `Платная приемка`, `Штраф` уменьшают общий P&L;
- операции без артикула не теряются;
- себестоимость выбирается на дату операции;
- неполное покрытие себестоимостью делает прибыль явно неполной.

Для расхождения фиксируются: показатель, период, WB source, WB Insight result, абсолютная/относительная разница, причина и решение. Необъяснённое существенное денежное расхождение блокирует повышение release stage.

P30 формализует эту сверку:

- policy: `ops/acceptance/wb_v1_metric_policy.json`;
- runner: `ops/data_accuracy_acceptance.py`;
- инструкция: `docs/DATA_ACCURACY_ACCEPTANCE.md`;
- результат входит в release evidence как `data_accuracy`.

Versioned tolerance policy является частью acceptance contract. Её нельзя ослаблять только ради прохождения релиза без объяснения и review.

## Spreadsheet как reference

Исходная таблица используется как coverage/business reference для областей, из которых вырос WB Insight. Она не имеет приоритета над официальным WB source и текущей исправленной semantic-моделью backend. Если старая Excel-формула и production semantic definition расходятся, причина и выбранный источник истины документируются в acceptance evidence.

## Изменение формул

Любое изменение бизнес-формулы должно включать:

1. изменение backend implementation;
2. regression test;
3. при необходимости migration/backfill strategy;
4. обновление документации;
5. запись в CHANGELOG, если пользователь увидит изменение результата;
6. повторную acceptance-сверку затронутых показателей.
