# Юридические документы и фиксация согласий

Этот документ описывает технический контур P27. Он не заменяет юридическую проверку текстов.

## Статус

Все тексты, встроенные в `services/legal_service.py`, имеют статус `draft` и явно помечены как требующие юридического утверждения. Наличие этого механизма не означает готовность продукта к `1.0.0-rc.N`.

До RC владелец сервиса и юридический специалист должны утвердить окончательные тексты, реквизиты оператора/продавца услуги, применимое право, правила возвратов, сроки хранения данных и иные обязательные условия. После утверждения меняются версия, текст и автоматически SHA-256 документа.

## Source of truth

Backend является единственным источником актуальной версии юридического документа.

Публичные API:

- `GET /legal/requirements/registration`
- `GET /legal/requirements/registration_legal`
- `GET /legal/requirements/billing`
- `GET /legal/requirements/marketplace_credential`
- `GET /legal/documents/{code}`

Frontend не может самостоятельно назначить версию документа. Перед действием он получает `code`, `version`, `sha256` с backend и отправляет их вместе с `accepted=true`.

Backend отклоняет действие, если отсутствует обязательный документ, версия устарела или SHA-256 не совпадает.

## Контексты

### registration

Для физлица и самозанятого:

- `terms`
- `privacy`

### registration_legal

Для юридического лица:

- `terms`
- `privacy`
- `personal_data`

### billing

Перед созданием платёжной попытки:

- `privacy`
- `offer`
- `refund_policy`

Согласия связываются с `payment_id`. Повтор того же Sber payment attempt по idempotency key не создаёт вторую пачку evidence.

### marketplace_credential

Перед сохранением WB credential:

- `privacy`
- `credential_policy`

Согласия связываются с ID сохранённого marketplace credential.

## Хранимое evidence

Таблица `legal_consents` неизменяемо фиксирует:

- `user_id`;
- код документа;
- точную версию;
- SHA-256 текста;
- контекст;
- ссылку на бизнес-объект (`payment_id`, credential ID или user ID);
- UTC timestamp принятия;
- HMAC IP;
- HMAC User-Agent.

Исходный IP и User-Agent специально не сохраняются в этой таблице. Это снижает объём персональных/технических данных при сохранении возможности сопоставить повторяющееся evidence при расследовании.

Для production рекомендуется отдельный `LEGAL_EVIDENCE_HMAC_KEY`. Если он не задан, текущая реализация использует `JWT_SECRET_KEY` как fallback для обратной совместимости; до RC отдельный ключ должен быть настроен.

## Изменение документов

Нельзя редактировать текст уже принятой версии «на месте».

Правильный процесс:

1. изменить текст;
2. увеличить `version`;
3. проверить новый SHA-256 через `/legal/documents/{code}`;
4. обновить CHANGELOG;
5. после deploy новые действия потребуют уже новую версию;
6. старые consent records продолжают ссылаться на старую версию и её SHA-256.

Перед stable-релизом архив утверждённых текстов каждой выпущенной версии должен храниться вместе с release artifacts или в другом неизменяемом хранилище.
