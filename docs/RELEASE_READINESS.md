# WB Insight — готовность к релизу

Дата ревизии: **20 октября 2026 года**.

Этот документ описывает **текущее** состояние ветки `dev`. Исторические acceptance-кандидаты и старые доказательства не считаются текущим состоянием продукта; их техническая летопись хранится в `VERSION_HISTORY.md` и `RELEASE_EVIDENCE.md`.

## Текущий статус

Интеграционная ветка — `dev`. Базовый коммит перед P126: `57123c45f6eebfa72c46f682e4bb68daddf56a99`. В него уже слиты P115–P125, включая транзакционный обновлятор, auth hardening, provider-neutral release acceptance, branch-policy tooling и сквозную операционную диагностику с центром инцидентов.

`main` остаётся веткой опубликованного стабильного релиза и не должна использоваться как рабочая интеграционная ветка.

Стабильный релиз **пока не разрешён**: после закрытия кодовых замечаний аудита остаются административная защита основных веток и фактическая production-like приёмка на выпускаемом коммите.

### P116 — отказоустойчивый обновлятор — закрыто

Обновление переведено на транзакционный сценарий:

1. блокировка параллельного запуска;

5. зашифрованная точка восстановления PostgreSQL;

Актуальная процедура описана в `SYSTEMD_DEPLOYMENT.md` и реализована в `update.sh`, `ops/update_systemd.sh`, `ops/publish_frontend.sh`.

### P117 — серверный выход и защита публичной авторизации — закрыто

- logout отзывает серверную версию сессии и очищает refresh-cookie;
- ранее выпущенные access/refresh JWT после отзыва не восстанавливают сессию;
- login и registration ограничиваются по частоте;
- публичные проверки email/телефона/ИНН больше не раскрывают существование аккаунта;
- production rate-limit использует Redis и при недоступном хранилище закрывает публичный auth-контур безопасной ошибкой;
- персональные идентификаторы не сохраняются в ключах rate-limit в открытом виде.

Подробности — `SECURITY.md`.

### P118 — независимая от провайдера почтовая приёмка — закрыто

Release acceptance больше не требует RuSender по имени. Проверяется реальный эффективный транспорт и его возможности:

- `ready=true`;
- наличие фактического provider code;
- `transactional=true`;
- готовность email verification;
- готовность password reset;
- фактическая доставка через provider-neutral inbox hook.

`SMOKE_EXPECTED_MAIL_PROVIDER` используется только как необязательная дополнительная фиксация конкретного окружения. Текущие адаптеры SMTP, RuSender и Resend проходят через один контракт возможностей. Подробности — `RELEASE_SMOKE.md` и `MAIL_PROVIDERS.md`.

В этой ревизии:

## P126 — архивирование журналов — техническая часть

Для `audit_events` и `operation_log_events` добавлен read-only архиватор `ops/archive_logs.py`:

- серверное пакетное чтение без загрузки всего журнала в память;
- gzip JSONL с сохранением UUID/дат/Decimal без преобразования денежных значений во `float`;
- SHA-256 и манифест с количеством строк и диапазоном времени;
- атомарное завершение через `.partial`, права `0600/0700`;
- повторная проверка архива без доступа к PostgreSQL;
- самопроверка в `Release integrity`;
- отсутствие команды purge и отсутствие обхода append-only триггеров.

Кодовая готовность к архивированию закрывается P126. **Политика retention ещё не считается утверждённой**: владелец/юрист должны определить фактический срок хранения и допустимость удаления, а оператор — подтвердить off-host хранение и восстановимость архива. Подробности — `LOG_RETENTION_ARCHIVE.md`.

## Обязательные проверки перед повышением стадии

На **точном коммите**, который планируется выпускать, должны завершиться успешно все шесть основных workflow:

1. `Frontend build`;
2. `Backend security`;
3. `Database migrations`;
4. `Release integrity`;
5. `Systemd updater`;
6. `Release smoke contract`.

Зелёный запуск на предыдущем SHA не переносится на новый кандидат автоматически.

Дополнительно для beta/RC/stable нужны соответствующие evidence из `RELEASE_SMOKE.md` и `RELEASE_EVIDENCE.md`.

## Блокер: защита `dev` и `main`

Проверка 15 октября 2026 года показала:

- GitHub branches API сообщает `protected=false` для `dev`;
- repository rulesets API возвращает пустой список;
- через используемую GitHub App недоступно чтение/изменение административной branch-protection конфигурации.

Поэтому **ветки нельзя считать защищёнными только потому, что CI зелёный**.

До stable владелец репозитория должен включить в GitHub административные правила для `dev` и `main`:

- изменения только через pull request;
- запрет force-push;
- запрет удаления веток;
- обязательный актуальный branch перед merge;
- обязательное успешное прохождение согласованного набора проверок;
- для `main` — merge только через release/release-candidate PR из проверенной интеграционной линии.

После включения правил необходимо повторно проверить фактическое состояние через GitHub API/UI и зафиксировать результат в release evidence. Пока это не подтверждено, пункт управления ветками остаётся **релизным блокером**, а не закрытой документационной формальностью.

## Что ещё необходимо доказать на выпускаемом коммите

Локальные и GitHub Actions проверки не заменяют production-like acceptance. Перед стабильным релизом требуется:

- upgrade существующей PostgreSQL и отсутствие schema drift;
- реальный seller account Wildberries и полный заявленный sync;
- независимая сверка финансовых показателей с исходными строками/официальными WB-источниками;
- подтверждённая реальная доставка verification/recovery на выбранном mail transport;
- проверка платёжного контура в согласованном sandbox/production-подобном режиме;
- backup/restore drill;
- desktop и mobile browser smoke;
- проверка onboarding обычного пользователя от регистрации до первой полезной аналитики;
- фиксация sanitized evidence на **том же Git SHA**, который выпускается.

## Исторический кандидат `0.9.0-beta.1`

Ветка `release/0.9.0-beta.1-acceptance` и SHA `71aa437198f872a4285a4ee7539b771b097acd42` остаются историческим свидетельством состояния сентября 2026 года. Они **не являются текущим release candidate** и не доказывают готовность более нового `dev`.

Исторические утверждения про обязательный RuSender также относятся только к старому acceptance-контракту. Текущий контракт описан в `RELEASE_SMOKE.md`.

## Критерий разрешения stable

Stable можно разрешить только когда одновременно выполнено следующее:

- кодовые пункты аудита закрыты и находятся в `dev`;
- `dev` и `main` фактически защищены административными правилами;
- exact-head CI зелёный;
- production-like acceptance и обязательные evidence относятся к exact выпускаемому SHA;
- нет необъяснённых расхождений финансовых метрик;
- обновление и восстановление подтверждены на целевом окружении;
- срок хранения audit/diagnostic журналов утверждён, а архивная копия хранится и проверяется off-host;
- клиентский onboarding понятен без административного аккаунта и внутренних знаний разработчика.
