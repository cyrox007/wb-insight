# Требования к доступу Wildberries для WB Insight

Актуально для текущего продукта WB Insight и модели WB API на 15 сентября 2026 года.

## Обязательные реквизиты самого WB Insight

WB Insight — облачный партнёрский сервис. Для production-доступа к данным продавцов backend обязан иметь:

- `WB_SERVICE_ID` — ID/asid WB Insight;
- `WB_SERVICE_SECRET` — сервисный секрет Wildberries.

Сервисный секрет можно получить двумя способами:

- при регистрации сервиса в Каталоге решений Wildberries;
- до готовности к Каталогу через `business-solutions@rwb.ru` — команда WB API выдаёт сервисный секрет и настраивает лимиты.

Без этих реквизитов production-приложение не должно принимать кабинеты Wildberries и не должно обращаться к seller API.

## Токен продавца до регистрации в Каталоге

Допускается **Базовый токен (Base token)**. Он подходит облачному сервису, который ещё не представлен в Каталоге решений.

Продавец создаёт отдельный токен для WB Insight и выбирает уровень доступа **Только чтение**.

Обязательные категории текущего продукта:

- Контент;
- Аналитика;
- Цены и скидки;
- Статистика;
- Продвижение;
- Финансы.

Эти категории соответствуют production-контурам WB Insight: карточки товаров, аналитика/воронка/хранение, цены, заказы и продажи, реклама и финансовый отчёт.

Важно: Base token партнёрского сервиса **не используется сам по себе**. Каждый запрос дополнительно подписывается `X-Client-Secret` WB Insight.

## Токен продавца после регистрации в Каталоге

Основной вариант — **Сервисный токен (Service token)**, созданный продавцом именно для WB Insight. В JWT поле `for` должно иметь вид `asid:<WB_SERVICE_ID>`.

Для каждого запроса как с Base, так и с Service token backend передаёт два заголовка:

- `Authorization: Bearer <seller-token>`;
- `X-Client-Secret: <WB_SERVICE_SECRET>`.

Service token другого авторизованного сервиса отклоняется.

После публикации в Каталоге также имеет смысл перейти на **OAuth 2.0** как более удобный onboarding без ручного копирования токена. Это отдельный этап после базового production-релиза.

## Что WB Insight не принимает

- **Personal token** — предназначен для собственных программ/on-premise и не должен передаваться стороннему облачному сервису;
- **Test token** — предназначен только для sandbox;
- токен без одной из обязательных категорий;
- токен с правом записи вместо «Только чтение»;
- истёкший токен;
- отозванный или неактивный токен;
- Service token другого авторизованного сервиса.

## Проверка при подключении

Backend:

1. декодирует JWT локально;
2. определяет тип по `acc`;
3. читает реальный срок действия из `exp`;
4. читает продавца из `sid`;
5. для Service token проверяет `for=asid:<WB_SERVICE_ID>`;
6. проверяет битовую маску категорий `s`;
7. требует бит `30` — «Только чтение»;
8. выполняет live-проверку `GET https://common-api.wildberries.ru/ping` с `Authorization` и `X-Client-Secret`;
9. только после успешной проверки шифрует и сохраняет токен продавца.

JWT-декодирование используется для чтения документированных claims, но не считается доказательством того, что токен не был отозван. Live `/ping` закрывает эту проверку перед сохранением.

## Жизненный цикл и ротация

WB API токен действует до 180 дней. WB Insight не рассчитывает срок самостоятельно: источником истины является `exp` в JWT.

Сервисный секрет WB Insight также действует 180 дней. Wildberries генерирует новый секрет за 30 дней до окончания старого, и оба действуют параллельно до истечения старого. Ротация должна выполняться без простоя.

`WB_SERVICE_SECRET` хранится только как backend production secret. Он никогда не передаётся во frontend, не показывается пользователю и не сохраняется в пользовательском профиле.

## Release dependency

До публичного production-релиза необходимо получить у Wildberries собственные `WB_SERVICE_ID` и `WB_SERVICE_SECRET`, настроить лимиты сервиса и проверить реальный Base-token flow минимум на одном тестовом кабинете продавца. После готовности сервиса — подать заявку в Каталог решений и перейти на Service token/OAuth onboarding.
