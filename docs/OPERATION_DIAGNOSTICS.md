# Операционная диагностика WB Insight

## Назначение

Операционный журнал нужен для разбора пользовательских инцидентов без ручного чтения разрозненных логов. Он связывает платежи, синхронизацию Wildberries, фоновые задачи и расчёт дашборда с конкретным пользователем и бизнес-операцией.

Главный идентификатор — `operation_id`. Для платежа он совпадает с `payment.id`, для фоновой синхронизации — с `sync_job.id`. HTTP-запросы дополнительно связываются через `request_id`.

## Где смотреть

В Панели управления доступен раздел **«Диагностика»**. По email или UUID пользователя он показывает:

- автоматические аномалии, требующие внимания;
- платёжные попытки и последовательность событий провайдера;
- кабинеты Wildberries без раскрытия токенов;
- состояние каждого набора синхронизируемых данных;
- последние фоновые задачи, число попыток и ошибки;
- воспроизводимый финансовый расчёт за последние 30 дней на канонической семантике P115;
- единую временную шкалу новых трассируемых операций.

Доступ управляется разрешением `diagnostics:read`. Оно выдаётся `super_admin`, `admin`, `manager` и `support`. Обычный пользователь и роль `analyst` этот раздел не получают.

## Платежи

Операция платежа журналирует создание попытки, повторное использование `Idempotency-Key`, ответы провайдера, подтверждение оплаты, активацию подписки, отказ или отмену. Исторические `PaymentEvent` также выводятся рядом с новым операционным журналом.

Полезная автоматическая аномалия `PAID_WITHOUT_SUBSCRIPTION` означает, что провайдер подтвердил оплату, но связанная подписка не найдена. Такой случай требует ручной проверки до изменения доступа пользователя.

## Wildberries и частичная синхронизация

Для каждого кабинета показываются безопасные метаданные подключения, а для каждой сущности — последняя попытка, последний успех и последняя ошибка. События фоновой задачи различают как минимум:

- локальная проверка подключения пройдена;
- недостаточно прав WB API (`WB_PERMISSION_DENIED`);
- функция недоступна кабинету (`WB_FEATURE_UNAVAILABLE`);
- авторизация отклонена (`WB_AUTH_FAILED`);
- ограничение частоты (`WB_RATE_LIMITED`);
- ошибка WB API (`WB_API_ERROR`);
- назначен повтор;
- сохранена контрольная точка;
- задача завершена или окончательно упала.

Это позволяет отличить ситуацию «токен принят, но нет данных» от частичного доступа, временной ошибки WB и зависшей фоновой задачи.

## Диагностика расчётов

Раздел повторно использует канонический `financial_semantics_p115`, а не отдельную формулу поддержки. За последние 30 дней выводятся продажи, возвраты, перечисление WB, комиссия, логистика, хранение, реклама, налог, себестоимость, ручные расходы, прибыль, ДРР, маржинальность и нераспределённые расходы WB.

Также показываются процент покрытия себестоимости и количество операций/товаров без стоимости. Неполная себестоимость формирует `CALCULATION_COST_INCOMPLETE`. Нераспределённые расходы WB формируют `UNALLOCATED_WB_EXPENSES`. Ошибка воспроизведения расчёта формирует `DASHBOARD_CALCULATION_FAILED`.

## Политика безопасности журнала

Журнал предназначен для подробной диагностики, но не является хранилищем секретов. Запрещено сохранять:

- полный номер карты, CVV/CVC, криптограмму;
- пароль пользователя;
- `Authorization`, cookies и session-токены;
- access/refresh JWT;
- сырой токен Wildberries;
- API-ключи и client secrets;
- секреты webhook и платёжного мерчанта;
- зашифрованные секреты из БД как диагностический payload.

Перед сохранением `input_data`, `output_data` и `metrics` проходит рекурсивная очистка. Подозрительные ключи получают значение `[СКРЫТО]`, а глубина, число элементов и длина строк ограничиваются. Идентификаторы сущностей (`token_id`, `payment_id`, `order_id`, `request_id`) сохраняются, поскольку нужны для корреляции и не являются секретами.

## Неизменяемость

`operation_log_events` является append-only таблицей. Alembic-миграция устанавливает PostgreSQL trigger, который отклоняет `UPDATE` и `DELETE`. У таблицы намеренно нет внешних ключей на изменяемые пользовательские сущности: диагностическая история должна пережить удаление платежа, кабинета или пользователя.

## Ограничение исторических данных

Новая временная шкала появляется только для операций, выполненных после установки P122. Исторические платежи, подписки, состояния синхронизации и задачи продолжают отображаться из существующих таблиц, но задним числом восстановить отсутствовавшие тогда шаги операции невозможно.

## Разбор инцидента

1. Открыть **Панель управления → Диагностика** и найти пользователя.
2. Сначала проверить блок «Требует внимания».
3. Для платежной жалобы раскрыть попытку оплаты и сопоставить статус банка с подпиской.
4. Для отсутствующих данных проверить кабинет, нужную сущность и последние фоновые задачи.
5. Для расхождения цифр открыть «Расчёт дашборда» и проверить состав показателя, покрытие себестоимости и нераспределённые расходы.
6. Для технической ошибки раскрыть событие операционного журнала и использовать `operation_id` / `request_id` для корреляции с серверными логами.
7. Никогда не просить пользователя присылать полный токен WB, реквизиты карты или секреты платежного провайдера.
